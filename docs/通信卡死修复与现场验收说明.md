# 通信卡死修复与现场验收说明

版本：1.2.5

日期：2026-09-03

## 1. 本次解决的问题

现场现象是 PLC/HMI 实际温度已经升高到约 50°C，但上位机长期停留在旧的 20–30°C；只有完全退出程序再打开才恢复。

旧实现可能出现这样的锁死链：同步 PLC 读取永久不返回 → 占住共享 I/O 锁和温度采集标志 → 关闭连接也等待同一条路径 → 自动重连无法建立真正独立的新会话。UI 继续保留最后一个数值，看起来像温度“卡住”。

v1.2.0 的恢复链为：

`TCP 建立 → MC 只读协议验证 → 单条指令硬超时 → 原子废弃旧连接代次 → 强制关闭旧 Socket → 新建独立 transport/锁 → 立即启动本代温度采样 → 新样本按代次/序号推送 UI`

即使旧的第三方同步调用暂时还未返回，它也没有资格接触新连接或把旧温度写回界面。
进程级 PLC 调用闸门和未结束任务熔断器会限制四台设备同时超时造成的线程/底层调用堆积；自动重连使用每台设备独立的指数退避和抖动，不会因一个 2 秒超时立即重连风暴。

v1.2.1 进一步把“四台设备会独立、随机开关机”定义成正式运行条件，不再假设四台必须同时在线：

- `自动待机`（默认）：设备关机属于正常工况，不记通信故障、不进入掉线列表、不触发黄灯；软件以 30～60 秒低频发现，设备开机后自动恢复连接与采集。
- `要求在线`：用于当班生产明确要求运行的设备；掉线或数据过期仍显示故障并触发黄灯，重连从约 5 秒退避起步。
- `停用`：完全停止连接与后台探测，也不参与三色灯判断。

设置在“系统设置 → 设备运行模式”中按 1～4 号设备分别保存。旧版 `config.json` 没有该字段时，会自动兼容为四台“自动待机”。

v1.2.3 修复了两项真实启动故障：WPF `Run.Text` 对只读显示属性尝试双向写回导致窗口启动崩溃；以及早期 `config.json` 缺少阈值/运行模式字段时被误判为配置损坏、四台 PLC 均不执行自动连接。旧配置现在保留原有 4 个 IP，并补齐既有的 90°C 与“自动待机”默认值。

v1.2.4 完成点击开窗链路的修复：设备卡片不再在鼠标按下事件内直接进入模态窗口，而是在完整的鼠标释放事件结束后由 Dispatcher 打开详情页；详情、设置、日志查询均增加开窗阶段诊断。新增隔离的 `--ui-smoke` 验证模式，会真实显示并完成四个主要窗口的 WPF 布局后自动退出，同时不会连接 PLC、不会驱动三色灯、不会生成或覆盖生产 `config.json`。

v1.2.5 将 PLC 连接改为有合法转移表的代次状态机：连接代次、不可变快照和 `PlcStatus.IsConnected` 投影在同一临界区提交；详细事件只接受服务当前的同一快照对象。温度样本与 `OnlineFresh` 原子提交，订阅者即使在 `PropertyChanged` 回调中同步断线，旧代状态也不能恢复在线。演示数据源使用相同生命周期，温度事件已进入 `IPlcService` 统一契约，管理层不再向下判断真实/演示实现类型。

## 2. 现场可见行为

- 正常：卡片显示最新温度和绿色“在线”。
- 超过正常刷新宽限：保留最后有效值供诊断，但主温度显示为 `--.-°C`，并明确显示“最后有效值/数据已过期”，状态变为黄色“在线 · 数据过期”。
- 自动待机设备未开机：显示“待机 · 等待开机”；探测期间显示“待机 · 正在探测”，主温度保持 `--.-°C`。
- 要求在线设备通信判定失败：显示通信故障/重连中，并进入掉线列表。
- 停用设备：显示“已停用”，不再建立 TCP/MC 会话。
- 新连接尚未取得第一条本代温度：旧值不得变回绿色实时值。
- 目标温度、三相电压或扩展寄存器读取失败：实际温度仍继续刷新，不再因此反复断开主连接。
- TCP 成功但 MC 只读验证失败：不发布在线状态，进入通信故障/退避。
- 实际温度寄存器为空、长度异常、范围异常或非有限值：不发布假 0°C；0°C 和负温仍被视为合法值。
- 首次 X/Y/M 快照只建立基线，不把默认全 False 与现场状态差异伪记为操作日志。
- 详情页扫描线常驻动画已改为静态装饰；图表动画继续关闭，避免视觉效果抢占 UI 线程。

## 5. 首次现场验收（只读）

首次验证只观察通信与显示，不执行 PLC 写入、输出点动作或工艺控制。

1. 关闭所有旧版本进程，确认任务管理器中没有残留 `MitsubishiMonitor.Demo.exe`。
2. 从上面的 v1.2.5 独立目录启动，确认文件版本为 `1.2.5.0`。
3. 核对 4 台 PLC 的 IP、5000 端口、温度寄存器类型（Word/DINT）和除数与现场 HMI 一致。
4. 先保持四台均为默认“自动待机”，只开其中一台，其余三台关机；确认开机设备在线且温度新鲜，三台关机设备显示待机，不出现通信故障风暴，三色灯为绿。
5. 依次切换“1 开 3 关”“2 开其余关”“多台开”“全关”；每次开机后允许最多约 60 秒完成低频发现。全关时三色灯应熄灭，而不是持续黄灯。
6. 将一台明确设置为“要求在线”，再在安全条件下只断开其网络或电源；确认该台进入通信故障/重连且黄灯生效。恢复后确认显示当前真实温度，而不是故障前旧值。
7. 对实际运行设备连续对照上位机与 PLC/HMI 温度至少 30 分钟，记录时间、两边温度和偏差；确认温度日志继续产生且时间连续合理。
8. 在现场真实的随机开关组合下运行至少一个完整工艺周期，关注是否仍存在重连风暴、明显 UI 卡顿或温度停留旧值。

## 6. 若现场仍出现旧值

请保留故障时间点前后日志，并记录：设备编号、PLC/HMI 实际显示、上位机显示、最后更新时间、卡片状态、网络是否可 Ping、是否自动重连成功。重点搜索诊断记录中的：

- `MitsubishiPlcService:IoTimeout`
- `MitsubishiPlcService:IoFailure`
- `DeviceManagerService:TemperatureStale`
- `自动重连`

如果日志显示通信持续成功且每次都读到 20–30°C，而 PLC/HMI 为 50°C，应优先核对两端读取的寄存器地址、Word/DINT 类型、缩放除数以及 PLC 程序是否更新同一个寄存器；这属于点表/现场数据源问题，不是 WPF 刷新卡死。
